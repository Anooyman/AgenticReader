3. 各维度详细分析¶

3.1 总体架构与依赖 — 5/10¶

做对了什么

  • src/memory/ 是全仓分层最干净的模块：12 文件 1443 行，只依赖 config/settings 与 core/llm，不反向碰 agents/ui。
  • src/pipeline/ + job_runner.py 有明确的并发纪律（串行车道注释、queue_transaction 锁、write_json_atomic 原子写），lifespan 的后台协程收尾（create_task + cancel + gather）写法正确。
  • services/scraper/ 是独立可替换子系统，通过 MCP stdio 与主进程解耦。
  • agents 包结构高度一致，内部循环引用普遍用 if TYPE_CHECKING: 限制在类型层。
  • 跨层取数普遍是有意识的函数级延迟 import，不是乱引。

问题（除上表 H10-H13 外）

  • CLI 与 UI 编排入口不同源 ⚠️ 修正：main.py 走 AnswerAgent+SearchAgent 直连路径，orchestrator 只被 UI 使用 → 同一问题 CLI 无长期记忆检索、行为不等价；且 job_runner/process_web_queue/memory_search 等后台车道把 provider="openai" 写死 6+ 处，用户在 UI 选 azure/ollama 不生效（复核确认 app_settings.py 已有 default_provider 配置源，只是没注入到批处理车道；根因是 load_config() JSON 与 .env 两套配置源并存）。
  • 删除逻辑两套实现 ✅ 确认：core/manager.py 的 delete_document_files 与 data.py HTTP 端点各写一份同类清理，UI 版还多出 parts 粒度选择，互相漂移风险高。
  • 三套任务状态机并存 ⚠️ 修正：TaskManager（文件式）、job_runner（webapp_jobs.json）、pipeline_queue（queue_store）三套状态字面量与落盘格式，无转换关系；重启恢复只覆盖 job_runner。复核修正：真正双写同一动作的是 job_runner+pipeline_queue（不是 TaskManager+pipeline_queue），且 queue_store 是三套里唯一做了 fcntl+原子写的。
  • scraper 依赖静态不可见 ⚠️ 修正：唯一接线是 settings.py 里的字符串 args: ["-m", "scraper.mcp_server.server"] + 相对 PYTHONPATH，靠 cwd 维系；复核修正「完全不可见」为「配置键引用可发现，包内实现不可见」，规模实为 16 文件 2637 行。

3.2 多智能体系统 — 6/10¶

做对了什么

  • 五个 agent 统一 state/nodes/tools/utils/prompts 自包含结构 + 依赖注入；orchestrator 通过 SubAgent 抽象 + function-calling schema 编排，接口干净。
  • 循环控制普遍有显式处理：递归上限跨 agent 边界显式传递、should_continue 硬约束、search 节点异常强制 is_complete=True 防挂死。
  • retrieval 的 tools_config 与实现严格对应，动态绑定带缺失告警和回退。
  • role 型提示词体系无悬空引用，全部经 config.prompts 聚合统一解析。

问题

  • H8 indexing 失败无路由 → 失败文档注册为 completed（这是多 agent 编排最实质的缺陷：用户对一个"成功"文档提问得到空答案且无从定位）。
  • H9 Answer 的「多轮推理」是死代码路径：evaluate→plan 循环可达，但回 plan 后立即被情况2 短路，永远产生不了第二轮工具调用。要么按 evaluate 意图让 plan 生成新 tool_calls，要么删掉循环边与 max_iterations 字段，别留「假 ReAct」误导维护者。
  • H10 的延伸：_retrieve_single 在 answer/tools.py:274-313 和 core/parallel/retrieval.py:209-245 几乎逐字重复两份，后者还直接增删 AnswerAgent 内部属性——RetrievalAgent 应提供 query() 公共方法收敛这条路径。
  • Orchestrator 容错空洞 ⚠️ 修正：900s 总预算只在每轮迭代开头检查，一次长时间的 deep_dive 工具调用可以无视预算；主循环 model.ainvoke 无 try/except，一次网络异常会炸穿整轮、绕过 EMPTY_ANSWER_FALLBACK。
  • 死提示词 ⚠️ 修正：plan 改为确定性逻辑后，TOOL_PLANNER 大段提示词 + INTENT_ANALYZER/QUERY_REWRITER 两个废弃 role + WEB_CONTENT_FETCH 共 150+ 行仍在字典里，全仓无调用点；tools_config 文件头「LLM 动态决定调用」的描述已与实现不符。
  • 低：SearchAgent 用 __del__ 清 MCP 客户端（GC 时机不可控，应换显式 aclose()）。

3.3 核心基础设施 — 6/10¶

做对了什么

  • LLM provider 抽象：ABC + 懒加载 + 各 provider 模型参数名差异的显式映射表；history 双层策略（LLM 总结失败自动回退截断）。
  • 向量层加载时自检 embedding 维度；并行检索 Semaphore + 单文档超时 + return_exceptions=True 隔离失败。
  • memory ingest 幂等设计扎实（内容 hash 去重、adapter 覆写清理被取代的尾块）；memory_browse 对 LanceDB 同步 IO 全部 asyncio.to_thread 包裹——这个正确范式可惜没有贯彻到 memory/search。

正确性缺陷（重点）

  • H4 章节并行历史污染 ✅ 确认：session_id 是 "summary"/"refactor" 两个字面量，且 summary/refactor 落在 DEFAULT 截断配置（30 条）里，并发越高分支越乱。修法：session_id 按章节隔离 + 用完 pop；更彻底是这条无状态路径直接绕开 RunnableWithMessageHistory。
  • H5 去重集合永不重置 ✅ 确认 → 「静默变差型」故障，排查成本极高。
  • H6 过滤失败降级丢过滤 ✅ 确认 → 兜底只应放宽单个维度（如仅去掉 dedup），且要给结果打 degraded: True 标记。
  • H7 embedding 键名两套 ✅ 确认 → 统一到一个读取函数，建表前实测维度而非静态猜表。

其余问题

  • LLM 失败被吞成空串 ✅ 确认：call_llm_chain 外层 except 一律 return ""，十余处调用点无法区分「调通但空」与「失败」；重试全靠 SDK 内置 max_retries=5，Ollama 连重试超时都没配；仓库自带 retry_on_error 装饰器却只装在 IO 路径、一次没盖到 LLM 调用。
  • 阻塞调用侵入事件循环 ✅ 确认：memory ingest 在 await 协程里用 fcntl.flock 排他锁且锁包住了全部 LLM await（争锁时卡整个 server，且 Windows 不可用）；memory/search.py 的 dispatch_tool_call 是同步函数内做 lancedb/embed 阻塞 IO——与 memory_browse 的正确做法自相矛盾；async_utils.run_async 的 nest_asyncio 重入是地雷（好在 run_parallel_* 无调用方）。
  • 记忆层 provider 硬编码 ✅ 确认：默认 "openai" 一路传字面量，Azure/Ollama 部署下表现为 memory 静默写不进/检索无结果；且两套记忆后端（同进程 LanceDB + 外部 LLM-Memory HTTP 桥，namespace 硬编码 "AATF"）各写各库、无统一检索入口。
  • scraper 两处 ✅ 确认（主线程核实）：downloader.py:187 把用户传入的 selector 直接插进 page.evaluate 的 JS 字符串（单引号包裹，可注入页面脚本）；retry.py/fallback.py 定义了 RetryStrategy/FallbackHandler 但只在 core/__init__.py 导入，浏览器下载路径根本没用——「降级/重试写了没接线」。
  • MCP 子进程配置依赖进程 CWD（settings.py 的相对 PYTHONPATH 与脚本路径）。

3.4 UI / API 层 — 4/10¶

做对了什么

  • job_runner 的车道拆分、超时、requeue 语义有清晰注释论证；memory 浏览层明确声明只读。
  • 前端 api.js 集中封装所有 fetch 端点，可一次性审计。

问题

  • C1 零鉴权 ✅ 确认：无 Depends/Security/鉴权中间件，WebSocket 不校验 Origin（Starlette 的 CORS 中间件管不到 WS）；/health 回显版本号、/docs 常开。
  • C2 目录穿越 ✅ 确认 + 下面三条读/服务接口同类问题 ⚠️ 修正：pdf.py/structure.py/chapters.py 的 BASE / 用户输入 均无 is_relative_to 断言，与删除接口同根因——复核确认单段 .. 的实际可达面限于目录上移一层内的探测/覆盖写（如 get_pdf_images(doc_name="..") 会列出 data/ 下的 png 列表），比「任意文件读取」轻，但根因相同应一并收敛。
  • H2 上传逃逸 ✅ 确认、H3 CORS ✅ 确认、H1 ChatService 串扰 ✅ 确认。
  • 调试信息暴露 ⚠️ 修正：config.py DEBUG=True 硬编码（未捕获异常会带堆栈返回 HTML）、REST 普遍 detail=str(e)、run_server reload=True 常驻。复核修正：WebSocket 的 traceback 输出其实有 DEBUG_MODE env 门控，默认不泄堆栈、但仍泄 str(e)——该项降级但仍成立。
  • 状态可靠性 ✅ 确认：task_manager/session_manager 用相对 CWD 的默认路径（与 config.py 的 PROJECT_ROOT 绝对路径并存 → 换目录启动会「写在一处、统计在另一处」），会话保存是非原子的 open('w')+json.dump，崩溃即截断 JSON 丢全部会话。

5. 附录：分析方法（Agent Teams 逻辑）¶

  • 编排方式：一个 workflow 脚本把分析拆为 5 个维度，每个维度先由 1 个「分析 agent」独立读代码产出结构化发现（含 file:line 证据、severity、修复建议），随后同一 agent 链上的「对抗复核 agent」逐条到代码里核实证据真伪与严重度是否恰当——即 analyze → verify 的流水线，item 间互不阻塞。
  • 规模：两轮共 14 个 subagent（5 分析 + 5 复核 + 2 分析 + 2 复核），另有主线程对两条未经复核的关键结论（indexing 失败注册、answer 单轮 ReAct）与 scraper 的两条结论做了直接代码抽查，共核实约 50 条主要论断。
  • 偏差控制：复核将 11 条发现从原 severity 修正（如热切换 provider 从 high→medium 因无生产调用点、异常静默从 high→medium 因 87% 捕获仍有日志），并纠正了若干计数类错误（scraper 文件数、测试文件数、README 占比）。个别 agent 层结论标注「unverified」是因为其复核输出未回填，其中两条最重要的已由主线程人工核实。
